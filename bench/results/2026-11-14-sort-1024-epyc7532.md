## 실행 조건

- 실행 명령 (전체): 커밋 `3b5a072`를 clone한 깨끗한 폴더에서 빌드하고, 1분 기다린 뒤 3회 연속 실행

```bash

cmake --preset bench

taskset -c 2 ./build/bench/bin/bench_selftest --csv bench_selftest.csv
```

- 부하 (uptime, 1분 평균): 실행 1 0.52, 실행 2 0.66, 실행 3 0.92. 측정 프로세스 자신이 1 가까이 더함

- 동시에 돌던 작업: 같은 계정의 ITCH 데이터 다운로드 `wget`(CPU 약 4%, CPU 3에서 실행, 네트워크·디스크 I/O), 다른 사용자의 프로세스(낮은 CPU 사용)

## 비고

- 이상값: 세 실행 모두 표본의 99.1–99.6%가 `[16384, 32768)` ns 구간에 있습니다. 실행 1은 `[32768, 65536)` 구간이 8,786개로 실행 2·3(4,296개, 4,453개)의 두 배라 p99.9가 49.7 µs로 높습니다. max는 0.2–1.0 ms이고, 실행 2·3에는 `[524288, 1048576)` ns 구간이 각각 5개, 1개 있습니다. dropped는 0입니다.
- 측정 중 간섭: VMware 게스트라 vCPU가 물리 코어에 고정되어 있는지, 호스트의 다른 VM 부하가 어떤지는 알 수 없습니다. 같은 계정의 `wget`이 다른 CPU에서 계속 돌고 있었습니다.
- 해석: p50은 21.40–21.47 µs로 실행 간 차이가 0.3% 이내입니다. p99.9는 p50의 1.8–2.3배입니다. 타이머 오버헤드(median 50 ns)는 측정값의 0.3% 미만이라 이 대상에는 영향이 작지만, 10배 규칙상 이 서버에서는 약 500 ns보다 짧은 함수의 호출별 지연을 믿기 어렵습니다. 1 ms에 가까운 max는 하이퍼바이저나 다른 작업의 선점으로 보이며, 원인은 이 기록만으로는 알 수 없습니다.
- 같은 실행의 `sleep_100us`는 3회 모두 최솟값이 100,000 ns 이상(113,071–163,305 ns)이라 자체 점검을 통과했습니다. p50이 약 165.6 µs로 요청보다 65 µs가량 긴 것은 리눅스 기본 timer slack(50 µs)과 가상화의 영향으로 보입니다.
- 같은 빌드로 `ctest --test-dir build/bench`를 돌려 단위 테스트 24개가 모두 통과했습니다.
- 타이머 표의 분해능: 커밋 `3b5a072`의 출력은 0이 아닌 가장 작은 차이를 `resolution`으로 찍어 21 ns, 30 ns가 나왔습니다. 이 값은 같은 실행의 min과 같은 호출 비용입니다. 0인 차이가 없었으므로 한 눈금은 min 이하라는 것만 알 수 있어 `n/a`로 적습니다.
